# Architecture decisions

## Structure
- `src/app` holds routes only and stays thin. Shared UI lives in `src/components`, and site-wide constants in `src/config/site.ts` (the site name, Loopback, is defined once; the 88x31 button SVG is the one place it is drawn by hand).
- Planned, not yet created: `src/domain` (framework-free ring logic), `src/db` (Drizzle), `src/server` (repositories, authorization), `src/validation` (Zod), and `widget/` (standalone vanilla-JS widget with its own build, talking to the app only over HTTP).

## Decisions
- **Server Components by default.** Milestone 1 ships no client JS; the mobile menu is a `<details>` element.
- **Framework-free domain layer.** `src/domain` must not import Next or React, so the navigation engine is plain, unit-testable functions.
- **Multi-ring readiness.** Domain types will carry a `ringId` from Milestone 2, even with a single ring. URLs do not encode it yet.
- **Monochrome theme, light and dark** (replaced the green terminal theme, which had itself replaced the initial "warm off-white" brief): black and white, following the visitor's `prefers-color-scheme` (no toggle), in the spirit of the ring-amajig ring. The look of the earlier theme is kept where it is structure rather than colour: square bordered panes (`card`), a `$ command` line heading each section (`prompt`), tag chips (`tag`), `btn`/`back-link` utilities, and the VT323 `h1`. Tokens live in `@theme` in `globals.css` as `light-dark()` pairs, and their names did not change, so components flip without edits; they use token utilities, not raw hex. The accent is simply the foreground colour (black or white), and a button's hover fill is its inverse. Lightning CSS lowers `light-dark()` to a `--lightningcss-light/dark` toggle; it has only been checked by reading the compiled CSS, not in a browser.
- **Contrast (WCAG, background / surface / raised), light then dark:** foreground 17.4 / 16.1 / 14.6 and 15.8 / 15.0 / 13.7, muted 7.2 / 6.7 / 6.1 and 7.1 / 6.7 / 6.1, accent 21.0 / 19.4 / 17.6 and 19.7 / 18.7 / 17.0, button text on its hover fill 21.0 and 19.7. All exceed AA (4.5), computed from the token values.
- **Fonts and motion:** JetBrains Mono (body) and VT323 (display) via `next/font/google`, self-hosted at build time. Motion: cards fade, blur and rise in with a stagger (`reveal` utility, `--i` per card, capped at 10), lift with a hard offset shadow on hover, the loading card and header cursor pulse. A global `prefers-reduced-motion` rule shortens every animation and transition to near zero.
- **Member cards** are large on purpose: two columns from `md`, `min-h-72`, `p-8`, 2xl name and lg description, with the visit button pinned to the bottom.
- **`cacheComponents` is enabled** in `next.config.ts`. From Milestone 2, data reads need `'use cache'` or `<Suspense>` boundaries.
- **Testing:** Vitest (unit, `src/**/*.test.tsx`) and Playwright (e2e, `tests/e2e`, desktop and mobile Chromium). `@playwright/test` is pinned to 1.63.0 to match the locally cached Chromium revision 1243.

## Milestone 2: public webring
- **Data seam.** `src/server/member-repository.ts` is the only reader of members. It started on seed data and moved to SQLite in M4 without callers changing.
- **Navigation engine** (`src/domain/ring.ts`): order is join date, then id. Only active members are navigated to. A visitor from a member who is no longer active still gets previous/next from that member's position. A single active member is their own previous and next. Unknown ids resolve to `null`.
- **Redirect routes.** `/ring/next/[id]`, `/ring/prev/[id]` and `/ring/random[?from=id]` answer with a 302 to the member's site, or to the homepage if the request can't be resolved. The homepage fallback is built from `SITE_URL`, not from the request URL: behind a proxy or tunnel the request URL is the internal address (the live ring first redirected to `https://localhost:3200/`). They send `Cache-Control: no-store` and work with plain links and no JavaScript, which is what the M3 widget will use.
- **No separate directory page.** The homepage lists every active member as a card, so `/members` only exists as `/members/[id]` profiles.
- **Profile URLs** use the opaque stable id: `/members/[id]`. Inactive and suspended members have no public profile (404).
- **Known limitation (Cache Components).** A *first* request to an unknown `/members/<id>` returns HTTP 200 with the not-found page and `noindex`; later requests return 404. `dynamicParams` isn't available with `cacheComponents`, so this can't be switched off. Still present after M4 (the data is async now, which didn't change it).
- **Trusted URLs.** Redirect targets come from stored member URLs. Strict http(s) validation on submission arrives with Zod in M4/M5.

## Milestone 3: embeddable widget
- **Standalone.** Source is `widget/src/v1.js`: plain JavaScript with JSDoc types (checked by `tsc -p widget/tsconfig.json`), no dependencies and no bundler. `scripts/build-widget.mjs` copies it to `public/widget/v1.js` (gitignored, run by `predev` and `prebuild`) and fails above 3 KB gzipped. It never imports app code; it only knows the `/ring/*` URL contract.
- **Embed style.** A `<webring-nav member="ID">` custom element with plain fallback links inside. If the script is blocked, JS is off or a CSP interferes, the fallback links still work. Because it is a custom element rather than a script that inserts itself, it works with client-side routers.
- **No network calls.** The links point at the redirect routes from M2. The ring's address comes from the script's own `src`, so it can't be redirected elsewhere by attributes on the member's page and also works if the ring is self-hosted.
- **Safety.** Markup is built with `createElement`/`textContent` only. `member` must match `^[A-Za-z0-9_-]{1,64}$` and is URL-encoded; otherwise the fallback links stay.
- **Styling.** Shadow DOM isolates it from host CSS. It inherits the host's font and colour. Members customise with `--webring-color|background|border|font|radius|gap` and a `compact` attribute. Styles use constructable stylesheets (not subject to `style-src`), with a `<style>` fallback.
- **Serving.** `/widget/v1.js` is versioned (a breaking change ships as `v2.js`) and sent with `Cache-Control` (1 h + stale-while-revalidate), `Cross-Origin-Resource-Policy: cross-origin`, `Access-Control-Allow-Origin: *` and `nosniff` (see `next.config.ts`).
- **Install page.** `/widget` is a static server component: snippets, option reference, platform notes and live previews that run the real script. `SITE_URL` (env, default `http://localhost:3000`) feeds the snippets.
- **Deferred.** A ring parameter (routes don't encode a ring yet), an interactive generator, and checking that members actually installed the widget (M5).
- **Playwright** now runs against its own build on port 3100 (`reuseExistingServer: false`), because another app may be listening on 3000.

## Milestone 4: database
- **SQLite, not PostgreSQL** (a deliberate change from the original brief, chosen to avoid running a database server). Driver: `better-sqlite3` through Drizzle. One file, `DATABASE_PATH` (default `./data/loopback.db`, gitignored), WAL mode, foreign keys on. It needs a persistent disk and a single app instance, so it doesn't suit serverless hosting; Drizzle also supports Postgres if that changes.
- **Schema** (`src/db/schema.ts`, migrations in `drizzle/`, generated by `drizzle-kit`, never `push`): `rings` and `members`. Members belong to a ring (`ring_id`), so multiple rings need no schema change. Ids are generated by the database (`m_` + 8 hex characters). The `main` ring row is created by a migration; the fictional seed members are **dev-only** (`db/seed.dev.sql`).
- **Constraints are the safety net.** Members are added with raw SQL (no admin UI until M6), so the database itself enforces: http(s) URL without whitespace, unique URL per ring, name 1-60 chars, description at most 160, status in (active, inactive, suspended) with no default, valid ISO date, at most 5 tags (JSON array), 6-digit hex accent colour, https avatar, id format shared with the widget. SQLite treats a `CHECK` that evaluates to NULL as passing; the integration tests caught that for dates and the constraint uses `coalesce`. Zod (`src/validation/`) applies the same rules plus normalisation for the write paths that go through the app (M5/M6).
- **Foreign keys are per connection in SQLite.** The app and scripts turn them on; the `sqlite3` CLI doesn't unless you run `PRAGMA foreign_keys = ON;` first.
- **Repository.** `src/server/member-repository.ts` reads through Drizzle into the framework-free `Member` type, with `'use cache'`, `cacheLife({ stale: 60, revalidate: 60, expire: 3600 })` and tag `members`. Measured: a member added with raw SQL showed up in the API after about 100 seconds. The M6 admin will invalidate the tag for immediate effect.
- **Public API (read-only):** `GET /api/members` and `GET /api/members/[id]`. Whitelisted fields only (no status or ring), `Access-Control-Allow-Origin: *`, `s-maxage=60`. Errors are `{ "error": { "code", "message" } }` with 400 (malformed id) or 404. There are deliberately **no write endpoints**: nothing could authorise them before M6.
- **Builds read the database** (`generateStaticParams`), so `DATABASE_PATH` must point at a migrated file at build time. An empty ring uses a placeholder param.
- **Tests.** Unit tests are database-free (`npm run test:run`). `npm run test:integration` runs against a real SQLite file, `TEST_DATABASE_PATH`, deleted and rebuilt on every run; the reset script refuses any file not named `*.test.db` / `*.e2e.db`. Playwright resets and seeds `E2E_DATABASE_PATH` before it builds.

## Milestone 5a: applications and the "setting up" state
- **Scope change.** The owner chose to build authentication in M5 rather than M6 (see M5b); M6 now covers member editing, suspension and removal, statistics and moderation.
- **Applications** (`applications` table, `src/server/application-repository.ts`): pending / approved / rejected. A partial unique index allows one pending application per site. Contact email is personal data: required while pending, nullable afterwards so it can be purged, only ever read by the admin pages, never copied to `members` and never in a public API (tested). Purge recipe: `UPDATE applications SET contact_email = NULL WHERE status <> 'pending';`.
- **"setup" member status.** Approved members start as `setup`: the homepage shows a loading card (`$ setting up...`, no link, no ring number), but they are not part of the ring: `isActive` is false, so navigation and `/api/members` skip them and `/members/[id]` is 404. Their own widget still works (navigation works from any known member), so they can install it while waiting. `isVisible` (active or setup) drives the homepage.
- **Join form** (`src/app/join/`): a Server Action with Zod validation, a honeypot (fake success, nothing stored), a per-address rate limit (3/hour, or a shared bucket of 20/hour when no trusted address exists; only `TRUST_PROXY=true` reads `x-forwarded-for`, and it uses the **last** entry, the one our proxy appended; the first entries are the visitor's own claims and could be rotated to dodge the limits, the admin login's included. This assumes exactly one trusted proxy hop. IPv6 addresses are grouped by their /64 prefix (`src/server/client-address.ts`), because one connection owns a whole /64 and per-address limits could be dodged by rotating inside it; IPv4-mapped addresses count as the IPv4 address, and anything that isn't an IP falls back to the shared bucket. Checked on the live site: wrong logins with rotating fake leading `x-forwarded-for` values were all counted as one visitor and blocked, with IPv4 and IPv6 as separate buckets), and a global cap on pending applications (`MAX_PENDING_APPLICATIONS`, default 100). Invalid forms don't spend rate-limit budget. The rate limiter is in memory on purpose (no addresses are persisted); it resets on restart and doesn't span instances, and the database cap is the backstop. `APPLICATIONS_OPEN=false` is a runtime kill switch enforced in the action; the page itself always shows the form.
- **Migration note.** Adding `setup` to a CHECK made drizzle-kit rebuild `members` (copy, drop, rename). Verified on a populated database: rows, indexes and constraints survive.

## Milestone 5b: login and the admin page
- **Better Auth** (1.7, Drizzle adapter, SQLite). Email + password, **sign-up disabled**, 8-character minimum. The one account is created from a terminal with `npm run admin:create` (email from `ADMIN_EMAIL`, hidden password prompt; `--force` replaces it, which is also the password-reset path). The auth tables (`user`, `session`, `account`, `verification`) are in `src/db/auth-schema.ts`, written by hand to match `getAuthTables` in the installed package because the Better Auth CLI needs Node 22 and this machine has Node 20.
- **No public auth endpoints.** `/api/auth/*` is deliberately *not* mounted (it returns 404). Sign-in and sign-out are Server Actions that call `auth.api` directly. Reason: Better Auth exempts server-side calls from its rate limiter and, by default, trusts a client-supplied `x-forwarded-for`, so a public sign-in route could be brute-forced by rotating that header. Our own limiter (`src/app/admin/login/actions.ts`) allows 5 attempts per 15 minutes per trusted address, or 10 from one shared bucket when no address is trusted, and counts every attempt.
- **Authorisation is checked on the server, every time.** `requireAdmin()` (`src/server/auth.ts`) reads the session and requires the account's email to equal `ADMIN_EMAIL`; it runs at the top of every admin page and every admin Server Action. It returns an `AdminSession`, and the admin data and service functions require one as their first argument, so they cannot be called without the check (a type-level proof, tested with `@ts-expect-error`). `src/proxy.ts` only redirects visitors without a session cookie as a convenience; the tests show a forged cookie gets through the proxy and is stopped by the action guard.
- **Sign-in never creates a session for the wrong person.** A non-admin email is rejected before Better Auth is called, after hashing the password anyway so the response time doesn't reveal which email is the admin's. Wrong password and unknown email give the same message.
- **Sessions** last 8 hours, in an `HttpOnly`, `SameSite=lax` cookie. Over plain `http` (local development) the cookie is not `Secure`; in production set `SITE_URL` to the `https` address so it is. Signing out deletes the session row on the server (verified: replaying the old cookie shows no data).
- **Admin operations** (`src/server/admin-service.ts`): approve creates the member in the `setup` state and links it, in one transaction guarded by `WHERE status = 'pending'`; a site that became a member meanwhile rolls the whole approval back. Reject stores a private note. Mark live turns `setup` into `active`. Repeats are no-ops. Each successful action calls `updateTag("members")`, so the public site changes immediately instead of after the 60 s cache window.
- **Hardening of `/admin/*`:** `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`, `X-Frame-Options: DENY` plus CSP `frame-ancestors 'none'` (clickjacking on the approve buttons), and `Disallow: /admin` in robots.txt. Applicant sites are shown as plain text with a `rel="noopener noreferrer nofollow"` link.
- **Behaviour to know.** The admin pages read the session behind `<Suspense>` (required by Cache Components), so they need JavaScript in the browser, and a visitor holding a *stale* cookie gets an HTTP 200 shell whose body only redirects to the login page (a redirect inside a streamed boundary can't change the status). Verified that no admin data is in that response; without any cookie the proxy answers 307.
- **Auth settings are read lazily**, so a fresh checkout still builds and the public site runs without them; only `/admin` needs `BETTER_AUTH_SECRET` and `ADMIN_EMAIL`.
- **Moved to M6:** editing, suspending and removing members from the browser, statistics, moderation.

## Milestone 6a: member management and the audit log
- **Audit log** (`admin_events`, `src/server/audit.ts`). One row per admin action: when, who (admin id **and email as plain text**, no foreign key, so the log survives `admin:create --force`), action, target, a one-line summary and a JSON details object. It is **append-only**: database triggers abort any UPDATE or DELETE, even from raw SQL. Entries are written inside the same transaction as the change they describe, so a change and its record succeed or fail together (tested by making the audit insert fail). It never contains an applicant's contact email; a removed member is kept as a name, URL, status and join-date snapshot. Constraints validate the action name, target type, summary length and that details is a JSON object under 4 KB.
- **Operations** (`src/server/admin-service.ts`, all take the `AdminSession` proof): approve, reject and mark live (now logged), plus edit, change status and remove. Edit writes and logs only the fields that changed (before and after), refuses an address another member uses, and an unchanged form is a no-op. Status moves follow `src/domain/member-status.ts`: active and inactive swap freely, either can be suspended, suspended can only go back to active or inactive, nothing can move into `setup` (only an approval creates it) and `setup` becomes `active` through Mark live. Suspending requires a private reason (kept in the log only). Remove permanently deletes: the confirmation page makes you type the member's exact name, the linked application stays with its member link cleared, the site can apply again, and the member's widget keeps working from its old position until taken down, as for inactive members.
- **Pages** (all behind `requireAdmin()`, same hardening as M5b): `/admin` (pending applications and members in setup), `/admin/members` (every member, status filter from an allowlist, counts per status), `/admin/members/[id]` (edit form, status control, link to removal), `/admin/members/[id]/remove` (typed-name confirmation) and `/admin/log` (50 per page, newest first, details expandable). `AdminShell` is a static frame (nav and sign-out) so it prerenders; the session-dependent body sits in a Suspense boundary. Every member change calls `updateTag("members")`, so the public site updates at once.
- **Notices** after an action are a fixed lookup (`src/app/admin/notices.ts`), so a crafted `?notice=` can never reflect arbitrary text.
- **Shared form field** (`src/components/ui/form-field.tsx`) is now used by the join form and the admin forms.

## Iframe embed
- **One line, no script.** `<iframe src="{SITE_URL}/embed?url=https://your-site.com">` for sites that can't run a script (or won't). `GET /embed` (`src/app/embed/route.ts`) finds the member by site address (`findMemberByUrl`, after `siteUrlSchema` canonicalises the address), so members don't need to know their id.
- **Who gets the widget.** Active and `setup` members (`isVisible`, same as the widget). Unknown, inactive or suspended addresses and malformed queries get a blank 200 frame, never an error, so the response doesn't reveal why. Optional `fgcolor` and `bgcolor` take 3 or 6 hex digits without `#`; invalid colours are ignored.
- **Static HTML by hand** (`src/server/embed-html.ts`): no JavaScript, images or external requests. The design is `◀ [ring] name_ ▶` (the five-dot mark inline to the left of the name, in the text colour, so there is still no image request), black on white or white on black (`light-dark()` defaults, so it follows the visitor's scheme; `fgcolor`/`bgcolor` override). Animation is CSS only: arrows blur in and nudge on hover, the name tilts toward the hovered arrow and the ring turns one step the same way (`:has()`), the trailing `_` blinks, all off under `prefers-reduced-motion`. Text scales with the frame (`clamp()` on `vw`/`vh`) instead of the script-based scale-to-fit the ring-amajig widget uses; the recommended size is 320x100, and very short frames get cramped. Links are relative to the ring's origin with `target="_top"`, so they work without JS and open in the visitor's window. The only dynamic values are the id (validated against `^[A-Za-z0-9_-]{1,64}$` again here), two validated colours and our own site name (escaped). There is deliberately no Random link in the embed (the script widget has one); it keeps the frame to the name and two arrows.
- **Headers.** `/embed` is the one page meant to be framed anywhere: CSP `default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors *`, `nosniff`, `noindex`, `Cross-Origin-Resource-Policy: cross-origin`, and a 60 s cache. Every other page now sends `X-Frame-Options: SAMEORIGIN` and `frame-ancestors 'self'` (`next.config.ts`); `/admin` keeps its own stricter rule.
- **Trade-offs.** No preview or test mode: unlike ring-amajig's `test=true`, a non-member sees a blank frame. Not customisable beyond two colours (use the widget for that), and the address in the URL must match the registered one exactly after canonicalisation, so a member who changes their address must update the snippet. Tests: `src/validation/embed.test.ts`, `src/server/embed-html.test.ts`, `src/app/embed/embed.integration.test.ts`.

## Deployment (one folder, two environments)
- **One checkout, separated by files.** Dev uses `.env.local`, `data/loopback.db` and `.next`; the live ring uses `.env.live`, `data/live.db` and `.next-live` (`distDir` follows `NEXT_DIST_DIR`, set only in `.env.live`). Next 16 already keeps `next dev` in `.next/dev`, but the e2e run (`npm run build` into `.next`) would overwrite a live build in the same directory, hence the second build directory.
- **Why `.env.live` is not an auto-loaded file.** `drizzle.config.ts`, `scripts/reset-db.mjs`, `scripts/create-admin.mjs` and Playwright call `loadEnvConfig(cwd)` without a mode, which `@next/env` treats as *production*; they would read `.env.production.local` and aim `db:migrate`, `admin:create`, `db:seed` and the e2e run at the live database (the seed wipes its target). `scripts/live.sh` sources `.env.live` explicitly, and the `live:*` scripts go through it. Process variables win over env files, so live values also override anything in `.env.local`.
- **Deploy** (`scripts/deploy-live.sh`, `npm run live:deploy`): refuses uncommitted changes, migrates `data/live.db`, builds, then restarts (or first starts) pm2 `loopback` bound to `127.0.0.1:3200`, and saves pm2's list.
- **Network path.** Cloudflare -> tunnel (`ring.5ee5.dev` ingress) -> port 3200 directly. nginx on this machine serves only 5ee5.dev (port 88) and is not in the path, so `x-forwarded-for` has exactly one trusted hop; putting another proxy in front would break the last-entry assumption (see M5a).

## Search and sharing
- **Per page:** title (`template` adds the site name; the home page's default adds the tagline), description, and an explicit canonical URL (`alternates.canonical`, resolved against `metadataBase` = `SITE_URL`). Canonicals are set per page rather than inherited, because the layout's fallback is the home page. Member pages (`/members/[id]`) get their name, description, `og:type=profile` and canonical.
- **Share card:** `src/app/opengraph-image.tsx` generates one black-and-white 1200x630 image (`next/og`, static at build) used for Open Graph and Twitter (`summary_large_image`). A page that sets its own `openGraph` replaces the inherited one, image included, so member pages list `/opengraph-image` explicitly.
- **Icons:** a ring of five dots (a ring of sites), white on black like the share card and the 88x31 button. `src/config/logo.ts` holds the dot coordinates shared by the header, the embed and the icons; `src/app/icon.svg` is drawn from them; `apple-icon.png` (180px, full-bleed) and `favicon.ico` (16, 32 and 48px, PNG-compressed entries) were rendered from it with `rsvg-convert`, so redraw all three together. Google asks for a favicon in multiples of 48px, which the SVG (any size) and the 48px icon satisfy.
- **Structured data:** the home page emits JSON-LD (`WebSite` plus an `ItemList` of active members), with `<` escaped so member-supplied text can't close the script tag.
- **robots.txt** (`src/app/robots.ts`): allows everything except `/admin`, `/ring/` (only redirects to other people's sites) and `/api/`. `/embed` is not blocked on purpose: it is kept out of the index by its `X-Robots-Tag: noindex` header, which a crawler can only read if it may fetch the page. Cloudflare's managed robots.txt is prepended on the live domain (search allowed, AI-training crawlers disallowed); our rules follow it.
- **sitemap.xml** (`src/app/sitemap.ts`): public pages plus one entry per *active* member (setup, inactive and suspended members are not listed), dated by their join day. Static pages have no `lastmod` rather than an invented one.
- **Left to the owner:** verifying the domain in Google Search Console and Bing Webmaster Tools (a DNS TXT record in Cloudflare) and submitting `/sitemap.xml`. Tests: `src/app/seo.integration.test.ts`.
